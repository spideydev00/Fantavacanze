# Recap sessione - Fantavacanze (30/04/2026)

## 1. CONTESTO STRATEGICO DELLA SESSIONE

L'obiettivo della sessione era analizzare e sistemare il caching delle notifiche
admin (daily challenge approval/rejection), che presentava più incoerenze:

- `notificationsBox.clear()` al cold start → distruggeva la cache offline ad ogni
  avvio, vanificando l'offline-first.
- Cache-first puro su un dato "condiviso multi-admin" → race condition: admin1
  approva → riga DELETE su DB → admin2 vede notifica fantasma per ore.
- `cacheNotifications` skippava le esistenti → aggiornamenti server invisibili.
- `getCachedNotifications` non filtrava per leagueId → switch lega mostrava
  notifiche di altre leghe.
- Cleanup chiamato PRIMA del cache write → ordine errato.
- Stream FCM cachava notifiche cross-league → inquinava la cache.
- Doppio delete su approve/reject (page + RPC server-side) → race + errore
  silenzioso sul secondo DELETE.
- Counter `NotificationCountCubit` triggerava refetch su delete invece di
  decrementare direttamente.

Decisione presa dopo discussione architetturale: passare a **NETWORK-ONLY quando
online + cache come fallback offline READ-ONLY**. La cache notifiche resta utile
solo per offline (UI mostrata, ma azioni distruttive disabilitate). La cache
delle daily challenges invece resta cache-first (è dato personale, stabile
entro la giornata).

Realtime Supabase: scartato come fuori scope.
Stale-while-revalidate: scartato dopo discussione (più semplice il network-only,
e UX della pagina notifiche non critica come una home).

### 2.2 Fix UX su approve/reject notifiche

**Bug osservato**: la 1ª notifica processata spariva correttamente, ma la 2ª
(arrivata via FCM) restava visibile dopo l'azione admin → serviva uscire e
rientrare nella pagina.

**Causa root**: `BlocListener<DailyChallengesBloc>` ascoltava lo state per
`operation == 'approve_challenge'/'reject_challenge'`. Ma `DailyChallengesLoaded`
estende `Equatable` con props `[challenges, leagueId, userId, operation]`.
Due approve consecutivi emettevano state identici (challenges/leagueId/userId
invariati + stessa operation) → flutter_bloc skippava l'emit per Equatable →
listener non triggerava → refetch non partiva.

**Fix in `notifications_page.dart`**:
- Rimosso `MultiBlocListener` con `BlocListener<DailyChallengesBloc>`.
- `_handleDailyChallengeApproval` / `_handleDailyChallengeRejection` ora:
  1. Capturano i bloc references prima dell'await.
  2. Fanno `_ensureOnlineForDailyChallengeAction()` (check + dialog).
  3. Dispatchano `Approve/RejectDailyChallengeEvent`.
  4. `await dailyChallengesBloc.stream.firstWhere((s) =>
       (s is DailyChallengesLoaded && s.operation == '...') ||
       s is DailyChallengesError);`
     → bypassa Equatable, intercetta sia success che failure.
  5. Check `mounted`, poi `notificationsBloc.add(GetNotificationsEvent())`.
- Approccio "fire-and-await" esplicito invece di listener reattivo:
  più leggibile, deterministic, immune al distinct-skip.

**Offline UX**: `_ensureOnlineForDailyChallengeAction` controlla
`serviceLocator<ConnectionChecker>().isConnected`. Se offline mostra
`AlertDialog` con titolo "Connessione assente", messaggio
"Per approvare o rifiutare le sfide quotidiane è necessaria una connessione
internet. Riprova quando sarai online." e bottone "Ho capito".
